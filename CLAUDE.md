# caldav-cli

A CalDAV client and MCP server. It ships as static Linux and signed macOS binaries on each GitHub release and as a container image (`ghcr.io/radiosilence/caldav-cli`).

## Git

- Work in PRs; never push to main. PRs are squashed; merge main into a branch rather than rebasing.
- Never push tags. CI tags and publishes when a release PR merges.
- Commits are signed.

## Changelog

`CHANGELOG.md` is generated by `scripts/changelog.py` and never edited by hand. Every change adds one fragment under `changelog.d/unreleased/<section>/`, named `<pr>-<slug>.md` and holding one `- **Lead.** Detail.` entry; to correct a note, edit its fragment. `just changelog --stdout` previews the result. The format is in `changelog.d/README.md`.

## Releasing

`just release patch|minor|major` (or an exact `X.Y.Z`) branches from main, bumps `Cargo.toml` and `Cargo.lock`, turns the unreleased fragments into the version and opens the release PR; the Release workflow does the same from GitHub. Merging it is the release: CD pushes the `vX.Y.Z`, `vX.Y`, `vX` and `latest` image tags, then creates the GitHub release with the binaries and the changelog section as notes. The image goes first because consumers poll releases and would pin a version with no image behind it. A push releases only when it changes the version; `gh workflow run ci-cd.yml` on main retries a release that failed part way. Both the Release workflow and publishing need the `RELEASE_TOKEN` secret; without it CD skips the release and says so.

## CI/CD

`.github/workflows/ci-cd.yml` is one pipeline: CI checks the change and ends in the `Checks` job, which is the only status the ruleset requires; CD runs on main after `Checks` passes and ships what CI built. The `changes` job decides from the diff which domains a change touches, and each CI job runs only for its domain, so a skipped job is expected and passes `Checks` (a failed or cancelled one fails it). The domains are `rust` (`src/`, `templates/`, `tests/`, the Cargo files, `.cargo/`; runs Check), `docker` (the musl Linux binaries and the image: on a pull request when `Dockerfile` or `Cargo.lock` changes, on main whenever `rust` does, since CD ships them), `deps` (the security audit: every push to main, since an advisory can land without any change here, and pull requests that touch the Cargo files or `.cargo/`), `changelog` and `workflows` (`.github/workflows/`, `.github/actions/`; runs actionlint). Changes under `.github/`, a release, a manual run and the twice-weekly cache-warming schedule run every domain. A pull request diffs against its base; a push to main against the last main commit whose run passed, and runs everything when that commit cannot be found. To add a domain, add an output and its path allowlist to `changes`, gate the new job on it with a job-level `if:`, and add the job to the `needs` of `Checks`; a new top-level source directory is invisible until it is in an allowlist.

The Linux binaries are built once, on `ubuntu-24.04` and `ubuntu-24.04-arm`, and the image only copies them in, so a local `docker build` needs `dist/` staged first (see the `Dockerfile`). CI pushes the image under the commit SHA on main; CD moves `main` and `sha-<short>` onto it, and a release adds the version tags and `latest` before the GitHub release attaches the same tarballs. The macOS binaries (aarch64 and x86_64) build on one runner, only on release pull requests (unsigned) and releases (signed and notarised).

## Check

```sh
just check   # actionlint, Cargo.lock clean, fmt --check, clippy -D warnings, tests, changelog
just fast    # what the pre-push hook runs
just fmt
```
